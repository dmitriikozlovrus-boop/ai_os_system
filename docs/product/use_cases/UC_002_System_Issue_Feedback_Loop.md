# Use Case: System Issue Feedback Loop

## 1. Цель

Позволить пользователю естественным языком сообщить, что Conductor неверно понял или выполнил предыдущее сообщение, сохранить ошибку в `SYSTEM ISSUES` и, когда безопасно, запустить исправление.

## 2. Пользовательский сценарий

Пользователь отправляет сообщение в Telegram. Conductor классифицирует его, задает уточнение или создает записи. Если результат неверный, пользователь пишет `Неправильно`, `/wrong`, отвечает через Telegram Reply или сразу формулирует исправление вроде `Нет, это товар` или `Дата неверная, завтра`.

Conductor связывает feedback с предыдущим interaction, сохраняет System Issue и предлагает исправить запись сейчас.

## 3. Вход

Источник: Telegram.

Формат: текстовое сообщение или Reply на сообщение бота.

Примеры:

- `Неправильно`;
- `Нет, это задача`;
- `Дата неверная, встреча завтра`;
- `Ничего создавать не нужно, это просто комментарий`.

Короткие ответы вроде `Да`, `Нет`, `Завтра`, `15:00` не считаются feedback без активного feedback state.

## 4. Выход

Пользователь получает подтверждение:

- ошибка зафиксирована;
- тип ошибки;
- критичность;
- понятый правильный результат;
- вопрос, исправить ли запись сейчас.

Системный результат: запись в Notion `SYSTEM ISSUES`.

## 5. Задействованные сущности

| Сущность | Роль в use case | Источник истины |
|---|---|---|
| Interaction | хранит исходный ввод, классификацию, pending, созданные записи и ошибки | `InteractionStore` |
| System Issue | фиксирует ошибку и ожидаемый результат | Notion `SYSTEM ISSUES` |
| Task / Study / Goods | исходные или исправленные пользовательские сущности | Notion базы Conductor |

## 6. Задействованные агенты и роли

| Роль | Статус | Задача в use case |
|---|---|---|
| Telegram / Lyuba | Active | принимает feedback и отправляет ответ |
| Conductor | Active | маршрутизирует feedback и запускает исправление |
| OpenAI | Active with fallback | классифицирует System Issue |
| Notion | Active | хранит System Issues и пользовательские записи |

## 7. Задействованные сервисы

| Сервис | Слой | Роль |
|---|---|---|
| Telegram | Input / Output | feedback и подтверждения |
| OpenAI | Intelligence | классификация ошибки |
| Notion | Data Layer | `SYSTEM ISSUES`, Task, Study, Goods |
| Local JSON Store | Runtime State | interaction history, feedback state, fingerprints |

## 8. Источники данных

- исходное сообщение пользователя;
- результат классификации;
- pending-вопросы;
- созданные записи;
- ошибки записи;
- feedback пользователя;
- Telegram Reply metadata.

## 9. Правила обработки

Порядок маршрутизации:

1. активный feedback state;
2. Reply на сообщение результата бота;
3. явная feedback-команда или конструкция исправления;
4. Pending;
5. обычная классификация.

Reply имеет приоритет над последним interaction. Если контекст не найден, feedback не теряется: бот просит прислать описание ошибки и правильный вариант одним сообщением.

Пользовательский feedback не дедуплицируется. Автоматические технические ошибки дедуплицируются по fingerprint 7 дней.

## 10. Что входит в use case

- feedback detection;
- поиск исходного interaction;
- сохранение System Issue;
- fallback без OpenAI;
- предложение исправить запись;
- повторная классификация правильного варианта после подтверждения;
- защита Pending от ошибочного перехвата.

## 11. Что не входит в use case

- самообучение модели;
- автоматическое изменение правил в GitHub;
- удаление или архивирование исходных записей;
- dashboard;
- массовая ретроспективная обработка ошибок.

## 12. Ограничения MVP

Исходные ошибочные записи не удаляются автоматически. При смене типа сущности Conductor создает правильную запись после подтверждения, а ошибочная исходная запись остается для ручной проверки.
