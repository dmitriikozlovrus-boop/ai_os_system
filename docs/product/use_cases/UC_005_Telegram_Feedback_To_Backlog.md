# Use Case: Telegram Feedback To Backlog

## 1. Цель

Пользователь может отправить через Telegram короткую, эмоциональную, неполную или позднюю обратную связь, а Conductor превращает ее в структурированный backlog без автоматического изменения кода.

## 2. Виды Feedback

Поддержаны четыре рабочих вида:

- `CONCRETE_ERROR` — конкретная ошибка результата;
- `GENERAL_PROBLEM` — общее наблюдение о повторяющейся проблеме;
- `IMPROVEMENT_IDEA` — идея или пожелание;
- `CORRECTION` — исправление текущего результата через существующий correction flow.

Также есть служебные виды `NOT_FEEDBACK` и `UNKNOWN`.

## 3. Нормализация

Conductor сохраняет исходный текст пользователя и отдельно формирует нейтральные поля:

- normalized title;
- normalized description;
- actual behavior;
- expected behavior;
- affected entity/database/component;
- severity;
- recommendation for backlog priority.

Эмоциональные формулировки не переносятся в нейтральное описание. Неизвестные факты не придумываются.

## 4. Interaction Context

Приоритет определения контекста:

1. активный feedback/correction state;
2. Telegram Reply;
3. явная ссылка на предыдущий результат;
4. последний pending interaction текущего chat;
5. последний recent interaction текущего chat;
6. feedback без конкретного interaction.

Отсутствие interaction не блокирует общую проблему или идею. Для конкретной ошибки без context неизвестные поля помечаются как неизвестные.

## 5. Clarification Policy

Уточнение задается только если без ответа невозможно определить действие.

Пример:

```text
Опять неправильно
```

без Reply и context переводится в `awaiting_feedback_clarification`.

Общие формулировки вроде `Ты часто теряешь даты` не требуют уточнения и могут попасть в backlog.

## 6. SYSTEM ISSUES

Для `CONCRETE_ERROR` создается запись в `SYSTEM ISSUES` по существующей схеме.

Заполнение:

- краткое описание — нормализованный заголовок;
- входные данные — исходный input из interaction или явная пометка, что context не найден;
- описание — исходный feedback, нормализованное описание, actual/expected behavior и context summary;
- причина ошибки — `Требует анализа.`;
- решение — `Не исправлено. Добавлено в backlog для анализа.`;
- способ обнаружения — `Пользователь`.

Для чистой идеи System Issue не обязателен.

## 7. IMPROVEMENTS

Conductor сначала ищет существующий открытый Improvement, затем предлагает новый.

Открытые статусы:

- `Идея`;
- `В работе`;
- `Отложено`.

Совпадение только по базе или одному общему слову не считается надежным.

Если match найден, пользователь получает предложение добавить случай в существующее Improvement. Relation и summary обновляются только после подтверждения.

Если match не найден, Conductor предлагает новый backlog item. Он создается после подтверждения или по явной команде `Добавь в backlog`.

## 8. Накопительная Summary

В тело Improvement добавляется managed section:

```text
## Сводка обратной связи
<!-- CONDUCTOR_FEEDBACK_SUMMARY_START -->
...
<!-- CONDUCTOR_FEEDBACK_SUMMARY_END -->
```

Summary содержит:

- количество связанных случаев;
- дату первого и последнего сигнала;
- основные проявления;
- ожидаемое поведение;
- счетчики источников;
- до 20 последних коротких сигналов.

Conductor не удаляет пользовательский content за пределами managed section. Если markers повреждены, страница не обновляется.

## 9. Duplicate Policy

Одинаковый короткий сигнал по одному Improvement не сохраняется повторно в течение 7 дней.

Relation System Issues дедуплицируются по Notion page ID.

## 10. Backlog Priority Recommendation

Conductor рассчитывает рекомендацию:

- `Низкий`;
- `Средний`;
- `Высокий`.

Факторы:

- количество сигналов;
- критичность;
- затрагивание Telegram -> Notion;
- риск потери данных;
- явная просьба пользователя.

Поле `Приоритет` существующего Improvement не меняется без отдельного подтверждения.

## 11. Telegram Backlog Browsing

Поддержаны команды:

- `Покажи backlog`;
- `Какие улучшения накопились?`;
- `Покажи открытые улучшения`;
- `Что нужно доработать?`;
- `Покажи только высокий приоритет`;
- `Покажи идеи`;
- `Покажи улучшения по Notion`;
- `Покажи второе`;
- `Подробнее про первое`.

Список ограничен 10 элементами и сохраняется в state текущего chat, чтобы номера не пересекались между чатами.

Просмотр Improvement не показывает Technical Spec автоматически.

## 12. Backlog Management

Поддержаны безопасные действия:

- изменить приоритет;
- отложить Improvement;
- вернуть в идеи.

Изменение статуса или приоритета требует подтверждения пользователя.

## 13. Feature Flag

Флаг:

```bash
FEEDBACK_BACKLOG_ENABLED=false
```

По умолчанию выключен.

При выключенном флаге correction flow, System Issues, existing Improvement flow и Technical Spec flow продолжают работать как раньше.

## 14. Fallback Без OpenAI

Fallback распознает базовые маркеры:

```text
неправильно
ошибка
снова
опять
часто
постоянно
нужно
хорошо бы
добавь возможность
не создавай
дубликат
не та база
неверная дата
не тот проект
```

Fallback не придумывает root cause, actual behavior или expected behavior, если они не следуют из текста или context.

## 15. Out Of Scope

- автоматический запуск Codex;
- GitHub branch/commit/push/PR из runtime;
- автоматическое изменение правил;
- автоматический Technical Spec для каждого Improvement;
- новая база Notion;
- изменение схем `SYSTEM ISSUES` или `IMPROVEMENTS`;
- отдельный Backlog Agent;
- самообучение или автоматическое изменение собственного кода.

## 16. Прогресс

Текущая оценка после сценария: 85%.
