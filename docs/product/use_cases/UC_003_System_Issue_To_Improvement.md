# Use Case: System Issue To Improvement

## 1. Цель

Цель сценария — после сохранения пользовательской ошибки в `SYSTEM ISSUES` определить, является ли она повторяющейся, и предложить пользователю создать или связать одно системное улучшение в `IMPROVEMENTS`.

Система не меняет правила, промпты или код автоматически. GitHub остается источником устойчивых правил и изменений кода, Notion хранит факты ошибок и предложения улучшений.

## 2. Актор

Основной актор — пользователь Telegram-бота Lyuba.

Conductor принимает feedback, сохраняет System Issue, ищет похожие ошибки, готовит предложение Improvement и ждет явного подтверждения.

## 3. Предусловия

- Пользователь уже отправил сообщение в Telegram.
- Conductor сохранил interaction context или получил orphan feedback.
- `NOTION_SYSTEM_ISSUES_DATABASE_ID` указывает на существующую базу `SYSTEM ISSUES`.
- `NOTION_IMPROVEMENTS_DATABASE_ID` указывает на существующую базу `IMPROVEMENTS`.
- `SYSTEM_IMPROVEMENTS_ENABLED=true` включает предложение и создание Improvements.
- У Notion integration есть доступ к обеим базам.

## 4. Основной сценарий

1. Пользователь сообщает об ошибке или исправляет результат.
2. Conductor создает запись в `SYSTEM ISSUES`.
3. Conductor отправляет пользователю обычный ответ feedback-flow и предлагает исправить запись сейчас.
4. Conductor запрашивает у Notion до 30 System Issues за последние 90 дней, отфильтрованных по `Тип ошибки` и `База данных`.
5. Conductor сравнивает новую ошибку с кандидатами через отдельный recurrence-анализ OpenAI.
6. Если OpenAI недоступен, используется детерминированная fallback-группировка.
7. Если повторяемость подтверждена, Conductor после correction confirmation предлагает создать Improvement.
8. Пользователь подтверждает создание.
9. Conductor создает одну запись в `IMPROVEMENTS` со статусом `Идея`.
10. В поле `Какие ошибки исправляет` записываются relation на новую и связанные System Issues.

## 5. Альтернативные сценарии

### Повторяемость не обнаружена

Conductor не отправляет дополнительное сообщение и не создает Improvement.

### Уже есть открытый Improvement

Если найден открытый Improvement со связанными ошибками или той же группой проблемы, Conductor предлагает связать новую ошибку с ним. После подтверждения relation обновляется, новый Improvement не создается.

### Пользователь отказался

Если пользователь отвечает `Нет`, `Не надо`, `Пропусти` или `Позже`, state очищается, Improvement не создается.

### Пользователь просит системное исправление

Если feedback содержит `создай улучшение`, `добавь правило`, `исправить системно` или похожую фразу, Conductor может предложить Improvement даже без достаточного числа повторов.

### Ошибка анализа

Если поиск похожих System Issues, OpenAI-анализ или проверка дубликатов падают, сохраненный System Issue остается успешным результатом. Ошибка пишется только в технический лог, рекурсивный System Issue не создается.

## 6. Notion Sources Of Truth

| База | Роль |
|---|---|
| `SYSTEM ISSUES` | источник конкретных фактов ошибок |
| `IMPROVEMENTS` | источник предложений системных улучшений |
| GitHub | источник устойчивых правил, тестов и кода после отдельной задачи |

Используемые поля `IMPROVEMENTS`:

- `Улучшение`;
- `Описание`;
- `Что изменить`;
- `Тип улучшения`;
- `Где изменить`;
- `Приоритет`;
- `Статус`;
- `Какие ошибки исправляет`;
- `Дата внедрения`;
- `Результат`.

## 7. Подтверждение пользователя

Improvement создается только после явного подтверждения:

- `Да`;
- `Создай`;
- `Создай улучшение`;
- `Да, создай`.

State создания Improvement отделен от correction state:

1. `awaiting_fix_confirmation`;
2. `awaiting_improvement_confirmation`;
3. `awaiting_existing_improvement_link_confirmation`;
4. Pending;
5. обычная классификация.

Короткий ответ `Да` интерпретируется по активному state. Одно `Да` не подтверждает одновременно исправление записи и создание Improvement.

## 8. Защита от дубликатов

Перед созданием нового Improvement Conductor ищет открытые записи:

- связанные с найденными System Issues;
- с тем же названием;
- с тем же типом улучшения и местом изменения.

Открытые статусы:

- `Идея`;
- `В работе`;
- `Отложено`.

Если открытая запись найдена, Conductor предлагает только связать новую ошибку с ней.

## 9. Ограничения MVP

- Нет автоматического изменения GitHub-файлов.
- Нет автоматического изменения правил или промптов.
- Нет автоматического PR.
- Нет автоматического закрытия System Issues.
- Нет автоматического статуса Improvement `Внедрено`.
- Нет векторной базы и периодического анализа всей базы ошибок.
- Для автоматических технических ошибок recurrence-flow не запускается.
- Поиск ограничен последними 90 днями и 30 кандидатами.
- При `SYSTEM_IMPROVEMENTS_ENABLED=false` System Issue и correction flow работают, но Improvement не предлагается.

## 10. Критерии успеха

- System Issue сохраняется независимо от результата recurrence-анализа.
- Одинакового `Тип ошибки` недостаточно для группировки.
- Три похожие ошибки формируют предложение Improvement.
- Improvement не создается без подтверждения.
- Relation `Какие ошибки исправляет` содержит выбранные System Issues.
- При существующем открытом Improvement новая ошибка связывается с ним.
- Fallback работает без OpenAI.
- Task, Study, Goods и feedback-flow продолжают работать.
